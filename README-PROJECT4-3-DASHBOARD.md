# Project 4.3 — Offline Security Monitoring Dashboard + Alert Triage

## Scope

A **snapshot-based, offline** dashboard for existing sanitized Cyranta alert JSONL outputs. It does **not** open a server port, call APIs, contact a third party, or monitor files continuously. It uses the Python standard library, with no additional dependencies. The UI is a self-contained HTML report with local JavaScript filtering and charts.

- **Input**: `telemetry/alerts.jsonl` generated by `python -m monitoring.detector` (not `telemetry/events.jsonl`, which may contain raw content if explicitly enabled).
- **Supported rule IDs**: CYR-DET-001, CYR-DET-006, CYR-DET-007.
- **Validations**: UUID request ID; recomputed alert ID; known severity, rule, event type, optional decision code; timezone-aware timestamp. Unrecognized alerts are counted and discarded.
- **Metrics**: total, high, medium, open triage, analyst-confirmed, by-rule counts, 14 most recent active UTC dates.
- **Dashboard**: offline HTML, interactive rule/severity/triage filters and ID/decision-code search. Source event text or arbitrary alert content is not placed in the report.
- **Triage**: local JSON file keyed by validated alert IDs; statuses `new`, `investigating`, `false_positive`, `confirmed`, `resolved`.
- **Privacy**: generated HTML includes sanitized request IDs/alert IDs, so protect it as local operational data and do not upload it to public hosting. It intentionally excludes raw prompts, model outputs, gateway user/resource IDs, arbitrary free-form strings, and bearer tokens.

## Install (on branch `project4-monitoring-dashboard`)

After extracting the ZIP to a temporary folder, copy only these files into the repository:

```
monitoring/dashboard.py
monitoring/tests/test_dashboard.py
README-PROJECT4-3-DASHBOARD.md
```

**Important: Update `.gitignore`** to include `telemetry/triage.json` and `telemetry/*.html`. Your existing `telemetry/*.jsonl` ignore rule should remain in place. These are generated local files, not source code.

## Commands (Windows PowerShell)

```powershell
cd C:\AI-Security\cyranta-ai-security-lab
$py = '.\.venv-agent\Scripts\python.exe'

# Use the existing sanitized alert file, not raw telemetry.
& $py -m monitoring.dashboard generate `
  --alerts telemetry\alerts.jsonl `
  --triage-file telemetry\triage.json `
  --output telemetry\dashboard.html

Start-Process (Resolve-Path telemetry\dashboard.html).Path
```

The dashboard should initially show **266 CYR-DET-001 / medium alerts**, assuming your existing `telemetry/alerts.jsonl` has not changed. The gateway demo files are intentionally **not** included in real alert totals.

To triage an existing alert, copy one `alert_id` from the dashboard, then:

```powershell
& $py -m monitoring.dashboard triage `
  --alerts telemetry\alerts.jsonl `
  --triage-file telemetry\triage.json `
  --alert-id '<paste-24-character-alert-id>' `
  --status investigating

# Regenerate to reflect persisted triage status.
& $py -m monitoring.dashboard generate `
  --alerts telemetry\alerts.jsonl `
  --triage-file telemetry\triage.json `
  --output telemetry\dashboard.html
```

Never use the literal angle-bracket placeholder as an actual alert ID; replace with an existing validated `alert_id`.

## Threat model and known limitations

1. The dashboard uses a static HTML snapshot. Refresh only after rerunning the `generate` command. No service, polling, login, RBAC or multiuser collaboration is provided.
2. Browser-side searching filters only already-approved metadata. The report cannot expose hidden raw event fields because they were removed server-side by the validator before HTML generation.
3. The triage file is a local single-user status store. It does **not** provide tamper-evident audit history, approvals, or evidence of a confirmed incident. `confirmed` means an analyst manually marked the detection as such.
4. Source JSONL files are not merged automatically. In particular, `project4-gateway-alerts.jsonl` is a synthetic demo file and must **not** be added to real incident metrics. To see live gateway detections, emit trusted sanitized gateway audit events via Project 4.2's `emit_gateway_audit`, rerun the existing detector, and regenerate the dashboard.
5. ChromaDB vulnerabilities are tracked separately and are not fixed by Project 4.3.
